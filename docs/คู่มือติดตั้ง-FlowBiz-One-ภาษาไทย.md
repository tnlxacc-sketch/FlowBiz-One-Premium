# คู่มือการติดตั้ง FlowBiz One สำหรับลูกค้า (ภาษาไทย)
**ฉบับตรวจสอบก่อนขาย | 13 ตุลาคม 2569 | รูปแบบ A: แยกเว็บไซต์และฐานข้อมูลต่อลูกค้า**

> **สำคัญ:** คู่มือนี้ใช้กับรุ่นที่กำลังเตรียมขาย ยังไม่ใช่ใบรับรองว่า UAT ผ่าน 100% ห้ามติดตั้งทับระบบสาธิตเดิม และห้ามนำข้อมูลลูกค้าจริงเข้าระบบก่อนทดสอบความปลอดภัยและกู้คืนข้อมูลผ่าน

## 1. ภาพรวม — ลูกค้าต้องเตรียมอะไรบ้าง

| รายการ | ใครเป็นเจ้าของ | ใช้ทำอะไร |
| --- | --- | --- |
| Supabase Project ใหม่ | ลูกค้า | เก็บข้อมูลสินค้า ลูกค้า ใบสั่งขาย คลังสินค้า บัญชีผู้ใช้ และเอกสาร |
| เว็บไซต์/โดเมน HTTPS ใหม่ | ลูกค้าหรือผู้ให้บริการตามสัญญา | ให้พนักงานเปิดเว็บ FlowBiz One |
| GitHub Repository สำหรับเผยแพร่เว็บไซต์ | ลูกค้าหรือผู้ให้บริการตามสัญญา | เก็บไฟล์หน้าเว็บของลูกค้ารายนั้น |
| พื้นที่ Backup แบบเข้ารหัส | ลูกค้า | เก็บไฟล์สำรองข้อมูลที่ไม่อยู่ในเว็บไซต์ |
| Supabase Project สำหรับทดสอบกู้คืน (TEST) | ลูกค้า/ผู้ให้บริการตามสัญญา | ทดสอบ Restore โดยไม่แตะระบบใช้งานจริง |

**ข้อห้าม:** อย่านำลูกค้าไปเชื่อม `ifanefgaiuzkbjtttiqn` เพราะเป็นฐาน FlowStock ที่เราใช้พัฒนามาก่อน

## 2. เริ่มต้นจากการเปิด Supabase

1. เข้าสู่เว็บไซต์ https://supabase.com/dashboard แล้วเข้าสู่บัญชีที่จะเป็นเจ้าของระบบลูกค้า
2. เลือก **New project** (สร้างโปรเจกต์ใหม่) ภายใต้ Organization ของลูกค้า
3. กรอกชื่อให้จำได้ เช่น `flowbiz-customer-a-prod`; เลือก Region ที่เหมาะกับลูกค้า และกำหนดรหัสผ่านฐานข้อมูลที่รัดกุม (เก็บไว้ในที่ปลอดภัย)
4. ตรวจสอบค่าใช้จ่าย/แพ็กเกจจริงก่อนยืนยัน เพราะแผนที่เลือกอาจมีค่าใช้จ่าย
5. เปิดหน้า **Project Settings → API** (การตั้งค่าโปรเจกต์ → API) แล้วจด **Project URL** และ **Publishable key** ไว้ให้ผู้ติดตั้งในช่องทางปลอดภัย
6. ห้ามนำ **Secret key, service_role key หรือ Database Password** ไปใส่ในไฟล์ `app.js` หรือส่งทางข้อความแชตสาธารณะ

**ผ่านเมื่อ:** มี Project URL ของลูกค้าคนละตัวกับฐาน Demo และสถานะโปรเจกต์พร้อมใช้งาน

## 3. ติดตั้งโครงสร้างฐานข้อมูล
**ขั้นนี้ให้ IT/ผู้ติดตั้งทำ** เพราะเกี่ยวข้องกับ SQL และสิทธิ์ข้อมูล ห้ามให้ผู้ใช้งานทั่วไปคัดลอก SQL มารันเอง

1. ใช้ชุดไฟล์ Migration ใน `supabase/migrations/` ของรุ่นที่ล็อกไว้และผ่านการทดสอบเท่านั้น
2. ติดตั้งตามลำดับที่กำหนดในคู่มือปล่อยรุ่น ไม่ข้ามลำดับ ไม่ติดตั้งลงฐาน Demo
3. ตรวจว่า Table, Function, Role, RLS, Storage bucket สำหรับ POD และ Policies ติดตั้งครบ
4. ตรวจการสมัครบัญชี (ปิด Self-signup), การสร้าง Admin คนแรก และการกำหนดสิทธิ์ตามหน้าที่
5. ตรวจการแยกบริษัท: คนของลูกค้า A ต้องไม่อ่าน/แก้/ส่งออกข้อมูลลูกค้า B ได้
6. เก็บบันทึกวันเวลา ผู้ติดตั้ง รหัสรุ่น และผลการตรวจสอบ

**ผ่านเมื่อ:** ตรวจ Security Advisor และทดสอบผู้ใช้จริง/ผู้ใช้ที่ไม่มีสิทธิ์แล้วผ่าน ไม่ใช่แค่สร้างตารางได้

## 4. สร้างเว็บไซต์ของลูกค้า

1. จัดเตรียม URL แบบ HTTPS ของลูกค้า เช่น `https://customer.example.com/flowbiz/` (เป็นตัวอย่าง ไม่ใช่ลิงก์จริง)
2. เปิด Supabase → **Authentication → URL Configuration** ตั้ง Site URL/Redirect URLs ให้ตรงกับเว็บของลูกค้า
3. ผู้ติดตั้งใช้เครื่องมือ `scripts/build-customer-site.mjs` ใน GitHub Branch `commercial/customer-isolated-deployment` โดยกำหนด 4 ค่า:
   - `supabaseUrl` = Project URL ของลูกค้า
   - `publishableKey` = คีย์สาธารณะของลูกค้า
   - `siteUrl` = URL เว็บของลูกค้า
   - `output` = โฟลเดอร์ใหม่สำหรับเก็บไฟล์เว็บ (ห้ามอยู่ภายใน Source เดิม)
4. ตัวอย่างคำสั่ง (สำหรับ IT; เปลี่ยนเป็นข้อมูลลูกค้าจริง):

```sh
node scripts/build-customer-site.mjs --supabaseUrl=https://CUSTOMER-PROJECT.supabase.co --publishableKey=sb_publishable_PUBLIC_KEY --siteUrl=https://customer.example.com/flowbiz/ --output=/tmp/flowbiz-customer
```

5. นำเฉพาะไฟล์ใน `output` ขึ้นเว็บไซต์ของลูกค้า
6. เปิดเว็บจากคอมพิวเตอร์และมือถือ ตรวจหน้าล็อกอินและการเชื่อมต่อฐานข้อมูลลูกค้า

**หมายเหตุ:** โค้ดหน้าเว็บใช้คีย์ประเภท Publishable เท่านั้น ระบบหลังบ้านต้องคุมสิทธิ์ด้วย RLS และ RPC อีกชั้นเสมอ

## 5. ตั้งค่าการใช้งานเริ่มต้น

1. IT สร้างบัญชี Admin คนแรกอย่างปลอดภัยและบังคับเปลี่ยนรหัสผ่าน
2. Admin เพิ่มพนักงานและ Role ได้แก่ Sales, Warehouse, Logistics, Owner, Admin
3. กรอก/นำเข้าข้อมูลตั้งต้น: คลังสินค้า สินค้า ลูกค้า ผู้ขาย รถ คนขับ ต้นทุนรายเดือน และ Stock ยกมา
4. ตั้งค่ากฎธุรกิจตามความตกลงกับลูกค้า เช่น การจอง Stock และนโยบายปรับยอดจากผลตรวจนับ
5. ทดลองอย่างน้อยหนึ่งวงจร: รับสินค้า → ขาย → จ่ายสินค้า → จัดส่ง → ยืนยันรับสินค้า → Invoice → ตรวจต้นทุนและกำไร
6. ตรวจว่า Dashboard และยอดคงเหลือตรงกับธุรกรรมจริง

## 6. สำรองข้อมูล (Backup) — ก่อนเริ่มใช้จริงทุกครั้ง

การ Backup ต้องครอบคลุม **ฐานข้อมูล PostgreSQL และไฟล์เอกสาร POD** มิใช่แค่ Export Excel

ผู้ติดตั้งต้องเตรียมเครื่องมือ Node.js 20+, `pg_dump`, `pg_restore`, `psql`, `tar` รวมถึงสิทธิ์เข้าถึงฐานลูกค้าและพื้นที่เก็บไฟล์แบบเข้ารหัส

สคริปต์หลัก: `scripts/backup-project.mjs`

ข้อมูลที่สคริปต์รับผ่าน **Environment Variables** ได้แก่ `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `COMPANY_ID`, `BACKUP_DIRECTORY`, `BACKUP_KIND`. อย่าใส่รหัสผ่านลงใน GitHub

ประเภทที่ใช้ก่อนเปิดระบบ: `BACKUP_KIND=PRE_GO_LIVE`

ผลที่ต้องได้: ไฟล์ Archive, ค่า SHA-256, รายงานจำนวนรายการ, ยอดเงินจาก Invoice และจำนวนเอกสารแนบ

## 7. ทดสอบกู้คืน (Restore) — ห้ามทำบนฐานจริง

1. สร้าง Supabase Project **TEST ใหม่** แยกจาก Production
2. ใช้ `scripts/restore-rehearsal.mjs` กับไฟล์ Archive ที่ได้จากขั้น 6
3. ระบุ `ARCHIVE_FILE`, `ARCHIVE_SHA256`, `TARGET_DATABASE_URL`, `TARGET_SUPABASE_URL`, `TARGET_SERVICE_ROLE_KEY`, `SOURCE_DATABASE_URL` และ `RESTORE_CONFIRM=RESTORE_TO_TEST_ENVIRONMENT`
4. ตรวจว่าระบบปฏิเสธการกู้คืนไปที่ URL ของฐานต้นทาง
5. หลัง Restore ตรวจยอดจำนวน Table, Sales/Cost/Freight/Other Cost, เอกสาร POD และลอง Login/เปิดรายการบนฐาน TEST
6. บันทึกวันที่ทดสอบ, ผู้ทดสอบ, ค่า SHA-256, โครงการ TEST ที่ใช้ และผล Pass/Fail
7. **ห้ามอนุมัติ Go-live** หากไม่มีหลักฐาน Backup และ Restore ผ่านครบ

## 8. เช็กลิสต์ก่อนส่งมอบลูกค้า

| ข้อทดสอบ | เกณฑ์ผ่าน |
| --- | --- |
| เปิด URL เว็บไซต์ลูกค้า | เปิดได้จริงทั้งคอมพิวเตอร์และมือถือ |
| เข้าสู่ระบบ | ทุก Role ที่อนุญาตใช้งานได้; คนไม่มีสิทธิ์ถูกปฏิเสธ |
| การแยกข้อมูล | ไม่เห็นข้อมูลบริษัทอื่น |
| รับ/จ่าย/โอน/ปรับ Stock | Movement และยอดคงเหลือถูกต้อง |
| Sales → Delivery → Invoice | ตัวเลขรายงานและกำไรตรงกับรายการจริง |
| รายงาน/Export/Print | ใช้ได้และตัวเลขตรงกัน |
| Backup → Restore | กู้คืนใน TEST สำเร็จ ตรวจตัวเลขและไฟล์แนบครบ |
| สิทธิ์ Admin และการบันทึก Audit | ถูกต้องและตรวจสอบย้อนหลังได้ |
| UAT | ทุกกรณีผ่าน ไม่มี Critical หรือ High defect ค้าง |

## 9. ถ้าระบบเข้าไม่ได้หรือข้อมูลไม่ตรง

- เว็บไซต์เปิดไม่ได้: ตรวจ URL, SSL/HTTPS, ไฟล์ที่ Deploy และ Browser Console
- Login ไม่ได้: ตรวจ Auth, User Profile, Role, Redirect URL และสถานะ Supabase
- ข้อมูลไม่ขึ้น: ตรวจ URL ฐานข้อมูลว่าชี้ Project ของลูกค้าถูกต้องก่อน ห้ามแก้ Role แบบเปิดสิทธิ์ทั้งหมด
- Stock ไม่ตรง: หยุด Post รายการเพิ่มในช่วงตรวจสอบ เก็บหลักฐาน Movement, Balance และ Audit
- Restore ไม่ผ่าน: **ห้าม** ทดลองซ้ำลง Production ให้ตรวจใน TEST และเก็บ Log

## 10. ความรับผิดชอบหลังขาย

ลูกค้าเป็นเจ้าของฐานข้อมูลและข้อมูลธุรกิจ ผู้ให้บริการดูแลโค้ดเวอร์ชัน การอัปเดต การติดตั้งและ Support ตามสัญญา กำหนดรอบ Backup, วันเก็บรักษา และ Recovery Objective ให้ชัดก่อน Go-live
